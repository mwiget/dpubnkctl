# AGENTS.md — dpubnkctl PoC repo

This repo drives a single F5 BIG-IP Next for Kubernetes (BNK) Proof-of-Concept
on bare-metal hosts with NVIDIA BlueField DPUs. It is consumed by humans
running `dpubnkctl` directly **and** by agentic CLIs (Claude Code, Gemini,
Aider, any OpenAI-compatible REPL) following the personas in `personas/`.

## Source of truth

- **`poc.yaml`** — full declarative state. Everything needed to redeploy this
  PoC from scratch lives here. If a field is missing from `poc.yaml`, it is
  not part of the PoC. Tear-down reads only this file.
- **`network-design-checklist.md`** — structured checklist the pre-sales SE
  walks through with the customer before provisioning. Each row asks a
  question, names the impact, and points at the `poc.yaml` field it
  populates. Run `dpubnkctl validate` after filling it in to confirm
  consistency.
- **`inventory/`** — discovery output (host classification, DPU inventory,
  Redfish probes). Regenerated by `dpubnkctl discover`.
- **`artifacts/`** — generated bf.conf renders, kubespray inventory,
  kubeconfig, helm values. Reproducible from `poc.yaml` + `inventory/`.
- **`journal/`** — append-only markdown journal, one file per phase or
  significant event. Owned by the doc-specialist persona.
- **`decisions.md`** — running decision log: what was chosen, why,
  alternatives considered. Owned by the pre-sales SE persona.

**Never commit secrets.** `.gitignore` excludes `keys/`, `*.tgz` (FAR keys),
`.jwt`, kubeconfigs. Reference them by path in `poc.yaml`, never by value.

## Personas

Three personas collaborate on this PoC. Each has a strict tool allowlist and
a clear handoff protocol. Read all three before starting:

- **`personas/pre-sales-se.md`** — solution architect; the only persona that
  talks to the customer. Owns scope, acceptance, and `decisions.md`.
- **`personas/lab-tech.md`** — DPU/BMC/rshim/mlxconfig specialist. Runs
  discovery and provisioning. Surfaces hardware/firmware issues.
- **`personas/doc-specialist.md`** — append-only journal keeper, generates
  the final lessons-learned report.

The pre-sales SE is the only persona authorized to ask the customer
questions or make scope decisions. The other two ask through the SE.

## YOLO / auto-approve tiers

Three tiers, declared per command:

1. **read-only** (always auto): `discover`, `cluster status`, `journal add`
2. **reversible** (auto with `--auto reversible`): writes to this PoC repo,
   `kubectl get/describe`, helm template
3. **destructive** (never auto without `--yolo` AND a matching PoC name):
   `provision dpu` (BFB flash, mlxconfig writes), `cluster up/down`,
   `deploy`, `destroy`. Modules marked `connectivity_risk: true` cannot be
   YOLO'd at all — they require an explicit confirmation prompt.

Agents must respect these tiers. If you're unsure, ask the pre-sales SE.

## How to work in this repo (any agent)

1. Read `poc.yaml` first. It tells you the BNK version, target topology,
   network plan, and which phases have completed (`status:` block).
2. Read the persona file matching your role. Stay inside its tool allowlist.
3. For any change, append to `journal/<YYYY-MM-DD>-<phase>.md` describing
   what you did, what you observed, and what failed. The doc-specialist
   curates these into the final report.
4. Never modify `poc.yaml` directly without the pre-sales SE confirming —
   it is the contract with the customer.
5. If you hit a documented failure mode (rshim consumed, EMBEDDED_CPU
   mlxfwreset, MFT DKMS, fabric-no-LACP), check `personas/lab-tech.md`
   for the runbook.

## Progress tracking — show every phase, not just the late ones

Maintain a visible task list covering the **whole pipeline** the operator
asked you to run, from the moment you accept the job. Most agentic CLIs
have a task primitive — Claude Code's `TodoWrite`, aider's tasks, the
equivalent in your runtime. Use it.

Create the task list *before* you run the first `dpubnkctl` command, with
one entry per phase the operator's goal will touch — typically a subset
of: `validate`, `discover`, `provision dpu`, `host network setup`,
`cluster up`, `cluster join-dpus`, `deploy network`, `deploy flo`,
`deploy cne`. Mark exactly one entry `in_progress` at a time; flip it to
`completed` as soon as the phase finishes (don't batch).

This gives the operator a live "where are we" view without having to
read full command output. A common past failure: agents only create a
task list once they hit the multi-step `deploy-*` group, so the operator
gets no visibility for the (often slowest) provision + cluster phases.
Don't do that.

If the operator's goal is a single phase, a one-entry list is fine — the
point is consistency, not bureaucracy.

## Smoke-testing the deployed Gateway

BNK 2.2.0 has **no global IPAM pool** — a `Gateway` applied without
`spec.addresses` stays at `Programmed=False, reason=AddressNotAssigned`.
Every Gateway must explicitly declare its IP, typically the
`bnk.external_selfip` value from `poc.yaml`.

Scaffold one with:

```
dpubnkctl gateway example --smoke-test --name demo --app-name nginx \
  | kubectl apply -f -
```

That emits a `Deployment` + `Service` + `Gateway` + `HTTPRoute` already
wired together. The Gateway's address comes from `poc.yaml`
`bnk.external_selfip` (override with `--address <ip>`). Once applied,
`curl http://<external_selfip>/` should return the nginx welcome page.

If you author Gateways by hand instead, fill in:

```yaml
spec:
  gatewayClassName: bnk-gatewayclass
  addresses:
    - type: IPAddress
      value: <bnk.external_selfip>
```

## Pinned versions (for this dpubnkctl release)

This binary builds for **BNK 2.3.0**:
- DOCA / BFB: 3.2.0 (`bf-bundle-3.2.0-113_25.10_ubuntu-24.04_64k_prod.bfb`)
- Release manifest: 2.3.0-3.2598.3-0.0.170
  (F5 Lifecycle Operator + CIS + cert-gen versions resolved at deploy
   time from this chart — see `dpubnkctl release-manifest pull`)
- Kubernetes: 1.30.14
- containerd: 1.7.23, runc: 1.2.1, pause: 3.10
- Default DPU MTU: 9000, Pod MTU: 8900

A different BNK release ships a different `dpubnkctl` binary with different
pins. Do not mix.

### Licensing in 2.3 (changed from 2.2)

In 2.2 the JWT and TEEM cert chain lived inside FLO chart values; in 2.3
the JWT goes into a `License` custom resource (`apiVersion: k8s.f5net.com/v1`)
and the TEEM endpoint is derived by the F5 Cluster-Wide Controller (CWC)
from the JWT's `jku` header — operators no longer pass it. The CWC's
own API certs are pre-created via the `f5-cert-gen` helm chart (pulled
from the release manifest) before FLO is installed.
